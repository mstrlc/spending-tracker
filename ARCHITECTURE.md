# new-spending-tracker: architecture and plan

A multi-tenant SaaS rewrite of `../household-spending-tracker`, built from scratch. The old app is a reference for domain rules only; its code is not ported.

## Decisions (2026-10-31)

| Area | Decision |
|---|---|
| Environment | Self-hosted on one Docker host behind a reverse proxy (`scripts/deploy.sh`, "Self-hosting" in the README; `SIGNUP=off`, `BEHIND_PROXY=true`, `SECURE_COOKIES=true`). For development each checkout (the main one or an agent's git worktree) runs its own API, web app and database through `scripts/dev.sh`, with one shared Postgres container (see "Worktrees" in `AGENTS.md`) |
| Backend | Kotlin, Ktor |
| Shared code | KMP `shared` module for server + future mobile apps (not used by web) |
| Database | Postgres 17 via Docker Compose, Flyway migrations, Exposed |
| Tenancy | *Household* is the tenant; users join one or more households via invites; every domain row carries `household_id` |
| Auth | Own email + password (argon2), server-side sessions in httpOnly cookies; OAuth / magic link later |
| API contract | Ktor publishes OpenAPI; web generates TS types + client with `openapi-typescript` |
| Web frontend | TypeScript 6 (TS 7 lacks the JS API openapi-typescript needs), React, Vite, TanStack Query, React Router, pnpm |
| Web UI | shadcn/ui (Radix, Nova style) on Tailwind CSS 4, lucide icons; components live in `web/src/components/ui` and are ours to edit. Theme tokens in `web/src/styles.css`; dark mode follows the system |
| Money | Integer minor units + currency code (household default currency) |
| Repo layout | Monorepo: `server/`, `shared/`, `web/`; Gradle Kotlin DSL |
| Tests | Ktor `testApplication` + Testcontainers Postgres; Vitest for web |

## Conventions

- Every domain row has `household_id`; cross-row references are composite `(household_id, id)` foreign keys.
- Routes under `/api/households/{householdId}` go through the `HouseholdAccess` plugin: non-members get 404.
- Editable rows carry `version`; updates send it in the body, deletes as `?version=`. A stale version is a 409 `version_conflict`.
- Rows still referenced can't be deleted (409 `*_in_use`); close accounts and archive categories instead.
- Every insert, update and delete of household data lands in `audit_log` (before/after JSON, actor) via Postgres triggers, so routes don't record anything themselves. The actor comes from `app.actor_id`, which `dbQuery` sets from the request's session user; new household tables need an `audit` trigger in their migration.
- API request/response models live in `shared` (`dev.spendingtracker.shared.api`) so mobile clients can reuse them. Response models have no default values: the JSON leaves out fields equal to their default, which would reach the web as `undefined`. Request models may have defaults.
- New references to a member are `(household_id, user_id) REFERENCES household_members ... ON UPDATE CASCADE`: claiming a member without a login moves the membership to another user id, and everything follows it.

### Web UI

- Build screens from shadcn/ui components (`web/src/components/ui`, imported as `@/components/ui/...`) and Tailwind utility classes. No hand-written CSS files; `web/src/styles.css` only holds the theme tokens and a few utilities.
- The components are copied into the repo, not a dependency: edit them when the design needs it (the table's padding and muted headers are such edits).
- App-level building blocks live in `web/src/ui.tsx`: `PageHeader`, `PageIntro`, `Field` (label, id and API field error for one control), `FormError`, `Surface` (the card a table sits on), `EmptyState`, `Summary` and `Money` (the figures at the top of a page), `RowMenu` (a row's actions behind "⋯"), and `Sheet` / `SheetBody` (the editor panel).
- The editor is a column beside the page (`Sheet` renders into the layout's `SheetSlot`), not shadcn's modal Sheet: opening it narrows the page instead of covering it. On phones it takes the whole screen.
- Confirm destructive actions with `useConfirm()` and ask for one line of text with `usePrompt()` (`web/src/dialogs.tsx`); never `window.confirm` or `window.prompt`.
- Save/delete undo lives in `web/src/undo.tsx`: `useUndoableSave()` shows a 6s `sonner` Undo toast after create/edit, and `useUndoableDelete()` hides rows via `usePendingDeleteIds()` and delays `DELETE` until the toast closes, the user navigates away (`UndoFlusher`), or `pagehide` fires (restoring the row with the error if it fails). `Toaster` is mounted once in `HouseholdLayout`.
- List tables sort by their column headers with `SortableHead`, `useTableSort` and `sortRows` (`web/src/sorting.tsx`): a first click sorts dates and amounts newest/largest first and text A–Z, a second flips it, a third goes back to the table's own order. Expenses, Income (within each person), Transfers, Merchants, Trips and Rules use it; the Inbox's headers set its sort menu.
- Forms use `NativeSelect`, not the Radix `Select`: real `<select>` elements work better on phones and in tests.
- Every amount gets the `amount` utility (Geist Mono, tabular figures). Colours come from the theme tokens only: neutral greys for the chrome, the near-black (white in dark mode) primary, and `destructive` for errors and deletes. Charts use `chart-1` (the largest) to `chart-6`.
- Colour carries meaning in small doses only, through `web/src/chips.tsx`: `KindChip` / `KindIcon` for what a record is (expense, refund, income, deduction, transfer, settlement, skip; `--tone-*`), `Chip` for a state (automatic, closed, expired, no login), `CategoryLabel` (a dot in the top-level category's hue), `Avatar` / `PersonLabel` (initials in the member's hue; joint is a neutral group icon), `AccountLabel` / `AssetIcon` (an icon per kind), `ConnectionStatus`, and `signedAmountClass` / `gainClass` (money in and gains green, losses red). Top-level categories and members take `--hue-1..8` in list order, so neighbours never share a hue.
- Icons come from `lucide-react`.

## Data model decisions (2026-11-14)

Settled after reviewing the old app's live data (exported to the gitignored `data/legacy/`, see its README). Most aren't built yet; the roadmap picks them up.

### People, ownership and debts

- ~~**Members don't need a login.**~~ (done 2026-11-14) A household member can exist without a user account and claim it later through an invite.
- **No person means joint**, everywhere a row can belong to someone: expenses, income, accounts, assets. There is no "unknown".
- **Who paid and whose it is are separate.** The account says whose money left; the expense says whose spending it is. A joint 10k IKEA purchase on one person's credit card is one joint 10k expense, never two halves.
- ~~**Joint or personal is filled in**~~ (done 2026-11-18) from the account (joint account → joint, personal account → that person), the merchant's past rows in the Inbox, and editable per expense (and per line). The web form follows the account until someone picks. Category or merchant rules for it were dropped: the defaults are right often enough.
- ~~**Debts between members come from mismatches:**~~ (done 2026-11-14)
  - a joint expense paid from a personal account makes the others owe their share to the payer (can be switched off per expense);
  - a personal expense paid from a joint account makes that person owe the others their share of the pot.
- ~~**Split ratio**~~ (done 2026-11-14) comes from rules with a valid-from date: a household default (usually by income), per-category overrides (groceries moved to 50/50), and a per-expense override.
- ~~**Repayments**~~ (done 2026-11-14, as settlements entered by hand until transfers exist) are transfers between members marked as settlements. Debts and settlements add up to one running balance between members; a settlement isn't matched to particular expenses. Settlements are neither income nor spending.
- ~~**Top-ups of a joint account**~~ (done 2026-11-15): configurable per household (`joint_funding`, V31): `pot` (default, top-ups are shown but don't create or settle debts) or `contributions` (top-ups are credited and withdrawals debited against the household split, capped at total joint-account spending so money still in joint accounts isn't owed; joint-account expenses adjust for category or per-expense splits, and unspent top-ups are shown as still in joint accounts).
- **No privacy inside a household**: every member sees everything.

### Accounts, bank feeds and transfers

- ~~**Accounts have a kind**~~ (done 2026-11-14): bank, credit card, cash, other. They can carry an IBAN.
- **A bank feed is not an account.** One account can have several feeds (Revolut Joint has CZK, EUR, HUF and DKK pockets), so feeds link many-to-one to accounts.
- **Feed sources sit behind one interface**: GoCardless Bank Account Data and statement-file upload to start, others later.
- **Bank rows keep** the bank's raw JSON, the booking and transaction dates, the native amount and currency, and what was decided about each: expense, income, transfer, settlement, duplicate or skipped, with links to what it became. Several bank rows can point at one expense.
- **Transfers are first-class**: a transfer pairs an outgoing and an incoming row, or one row and an account that isn't read. Paying off a credit card is a transfer; the card's purchases are the expenses, and what's owed on the card is a liability in net worth.
- **Inbox auto-filing**: the app files anything above a confidence threshold, whether from a person's rule or its own guess (transfer pairs, duplicates). Every automatic decision is stored as automatic, so it can be reviewed, counted and undone apart from human ones. The threshold starts strict: the old app's automatic pairings were wrong often enough to matter.
- **One rules table** maps bank rows (counterparty, IBAN, text) to an outcome: merchant, category, person, income source, or transfer/skip. It replaces the old app's separate merchant aliases and income payers.

### Spending

- ~~**Merchants are records**~~ (done 2026-11-14) with a name and a default category, so top merchants and subscriptions don't split on spelling. The bank texts that map to them come with the rules table.
- ~~**Split lines**~~ (done 2026-11-14; whose per line 2026-11-15): an expense can have lines with their own category, amount and whose that add up to its total, so one payment can hold one person's items, the other's and joint ones. E-shop orders can fill them in later.
- ~~**Refunds attach to the original expense**~~ (done 2026-11-14, `expenses.refund_of`), so it shows net in its own category and month.
- ~~**Foreign currency**~~ (done 2026-11-14): an expense can store the original amount and currency next to the household-currency amount everything adds up in.
- ~~**Trips**~~ (done 2026-11-14): a trips table, and an expense can belong to a trip (including a single lump sum booked for the whole trip).
- ~~**Business**~~ (dropped 2026-11-18): business money counts in the household like any other; there's no business tag.
- ~~**Recurring payments**~~ (done 2026-11-18, V45) are detected from history. Confirming one makes it a known recurring item with an expected amount and day, and the app flags when it changes or is missed. `recurring_payments` holds one row per merchant: `active`, `ended` (stopped, kept for the record) or `dismissed` (only stops the suggestion), with the expected amount, an interval (1, 2, 3, 6 or 12 months), an anchor date the due dates repeat from (the day clamped to shorter months), and optional category, account, whose and notes. `GET /recurring?today=` returns each payment's health on that day (`ok`, `due` while a charge may still come, `missed`, `changed` when the latest charge is more than 5% off, `upcoming`, `inactive`), last and next due dates, the last charge and missed dates, plus suggestions and the active payments' monthly cost. Charges are the merchant's expenses (refunds netted off) within 10 days of a due date, 20 for longer intervals. Suggestions (`recurring/Recurring.kt`, `detect`): monthly when charged in 3 of the last 7 calendar months with month totals within 25% and the latest in 45 days; yearly when two charges a year apart (±20 days) by similar amounts with nothing in between. Merging merchants moves the row along unless the target has its own. The Recurring page (under Money) lists active payments with chips for missed and changed ones (a changed one offers "Expect … from now on"), suggestions to confirm (a prefilled form) or dismiss, and ended and dismissed ones; the Overview's Subscriptions card links there. Not yet: rows still pending in the Inbox don't count as charges, so a charge not filed yet shows as missed.

### Income

- ~~**Gross lines and deductions**~~ (done 2026-11-14): income is recorded gross; health and social insurance advances (ZPMV, OSSZ) are deductions, so earned, deducted and net are all visible. Neither counts as spending.
- ~~**Two dates**~~ (done 2026-11-14): the month it was earned (what reports use) and the date it arrived (what links it to the bank row). A salary paid on 2 November counts for October.
- **Costs netted against an invoice** (the old "(odpočet z faktury)") are expenses paid out of that income, with no bank account; the income stays gross.
- Income can be joint.

### Assets and net worth

- ~~**Investments become assets**~~ (done 2026-11-14) with a kind: market (fund, stock, bond, crypto; can be priced from closing prices), savings, savings scheme (building savings, pension), receivable, vehicle, property, other (valued by hand). They share contributions, valuations and fees. Still to come: liabilities (loans, what's owed on a credit card) and savings balances read from bank feeds.

- ~~**Accounts the bank doesn't report**~~ (done 2026-11-21, V46): an account can get balance checks (`account_balances`; `/accounts/{id}/balances`), refused once the bank reports its balance. Its balance on a day is the nearest check moved by what the ledger recorded on the account since (or, before the first check, back to it): transfers in and out, earnings in, deductions (their own account or their earning's), expenses (refunds come back) and contributions paid from it. Money moved into savings stays a transfer. `Book.bankValue` falls back to it, so it counts in net worth and runway and for an asset following the account. A card's or loan's bank balance always counts as owed, whichever sign the bank uses (Raiffeisen reports its card as positive spending). `/assets/accounts` lists every account's value (bank, computed or none); `/assets/summary` adds `accountsMinor`, so net worth on /assets matches the Overview's, and the Assets page lists the accounts no asset follows.

### Reporting and planning

- **Saved = income − spending.** Money put into assets is part of saved; Invested shows how much of it went there.
- ~~**The Overview**~~ (filter done 2026-11-18) covers the whole household by default, filterable to joint or one person: `/overview?whose=joint|<userId>` counts spending by whose each expense or line is (`SpendingPart.ownerUserId`), income by recipient and investing by the asset's owner; net worth, money at hand and the bank data stay the household's, and runway measures them against the household's typical month. The Overview page has Everyone / Joint / each member tabs (`?whose=`, kept when paging months; `useMonthParam` now keeps other query parameters).
- ~~**Reports**~~ (done 2026-11-21): `GET /spending-report` totals spending over any period (`from`/`to`, open ends meaning the ledger's start and today), narrowed by category (subcategories included; `none` for uncategorized; `excludeCategoryId`, repeatable, leaves categories out with their subcategories, e.g. Groceries without Coffee beans), merchant (`none` for no merchant), account and whose, counted like the Overview (`loadSpendingParts`: lines, refunds netted in the original's month and category, investing left out unless it's the category asked about). It returns the total, expense count, every month with the average, the same dates a year earlier (periods up to a year the ledger already covered), breakdowns one level below the category filter and by merchant, and the latest 500 matching expenses. Without a category or merchant filter it also returns what went into assets (`investedMinor`, per month too), counted as on the Overview, by owner for whose and by paying account for an account; it never adds to the total. The Reports page (under Money) keeps the period (this month, the last 3, 6 or 12 months or 3 years, each from the 1st of a month up to today; a calendar year; all time; custom dates) and filters in the URL, draws months (years past 36 months) on an amount axis with each bar's figure, the average, a details card on hover or focus and investing as a striped segment on top (hidden from its legend), lists left-out categories as chips (added from "Leave out" or a category row), narrows on clicking a category, merchant or month, and opens an expense in the editor.
- ~~**Money flow**~~ (done 2026-11-21): the Overview's "Where the money went" card draws the month as a sankey (`web/src/overview/sankey.ts`, `MoneyFlow.tsx`): gross income by source (`Overview.incomeSources`, every source; sources under 2% or past the 6th summed as "Other income"), plus what was taken out of assets and, when the month cost more than came in, "From savings", flow into the month's income and out to deductions (`Overview.deductionsMinor`), spending by top-level category (under 2% or past the 10th summed), Invested and what was left over. It follows the whose filter; a category opens Reports on it for that month.
- **Budgets** are per category per month, separately for each person and for joint.
- **The forecast** projects coming months from confirmed recurring items and declared expected income.
- **Goals and the wishlist** are out for now.

### Importing the old app (done 2026-11-14)

- **Only expenses and income** already logged, keeping subcategories and trips; members, accounts and categories are created as needed (existing members without login). Bank rows, rules, budgets and net-worth snapshots come later, on demand.
- **The old app's automatic pairings are hints, not facts**: anything it decided as `bank-sync` (all transfer links, internal-transfer and duplicate skips) isn't imported as a decision; it can serve as a test set for the new matcher.
- **Cutover, re-imported 2026-11-15**: the household was reset and re-imported with the old app as the ledger before 2026-10-01 and the bank from then on. The import brings expenses, income and asset contributions dated before `CUTOVER` (2026-10-01, also `debtsFrom`) and no bank feeds, rows, transfers or pairings, so nothing old needs matching against bank rows. Every bank account the old app read becomes a ledger account of its own with its IBAN (the old app filed some savings accounts under a current account, which hid money moving between them). The old merchant aliases come out as a second file, `rules.json`: suggestion rules (text contains → merchant), added through `POST /inbox-rules`. The database before the reset is in `data/legacy/backups/`.
- **Bank data starts with the balances** (2026-11-15): every way rows come in (statements, syncs, imports) drops rows booked before the household's `debts_from` as well as before the feed's import-from date (`startOfBankData`), a sync asks the bank from there, and a new feed's import-from defaults to it in the web forms. Before that day the old ledger is the record.
- **Savings accounts** (2026-11-15, V35): account kind `savings` beside `bank` (shown as "Current account"), with `interestTaxPercent` (0–99, default 15: what Czech banks withhold; only savings accounts have one). Money in on a savings account from no counterparty, with interest in its text or no text at all (ČSOB books it at the month's end that way), gets the hint "Interest" and is suggested as income from "Interest" with `withheldTaxMinor` worked back from the rate (gross = net × 100 / (100 − rate)); the Inbox drafts the earning at the gross with "Tax on interest" as a deduction, so its net is what came in. The import marks "Spoření"/"spořicí" accounts as savings.
- **Old income** is already gross, so it imports as is (earned month = its month).
- **Old Investments expenses** become contributions to the household's assets (investment fund, building savings), recorded per asset with their amounts and dates.

## Roadmap

2. ~~**MVP slice**~~ (done 2026-10-31): sign up / log in, create household, accounts, expenses with categories.
   ~~Not yet: undo after save/delete.~~ (done 2026-11-15: `web/src/undo.tsx`)
   - ~~**Audit log**~~ (done 2026-10-31): trigger-written log of every create, edit and delete across households, members, invites, accounts, categories, expenses and income; the Activity page lists it by day with field-level before → after.
   - ~~**Overview**~~ (done 2026-10-31): the new landing page. The month's spending, income, saved and invested with month-end pace; a typical month (last 6 complete months, expensive outliers trimmed); 12 months of income vs. spending; unusual spending by category against the prior year; subscription radar; top merchants and income sources. Computed server-side (`/overview`) so mobile apps get the same numbers. Months before the ledger starts are unknown, not empty: the ledger starts at the first expense or income (since 2026-11-21 an asset's contributions only set it when nothing else is recorded, so an asset's history entered back from statements counts toward its cost and return without adding empty months to the baseline).
     ~~Not yet: import freshness, net worth and runway~~ (done 2026-11-16): `Overview.netWorth` is net worth on the month's last day (or today while it runs): the latest bank balance on or before it of every account no asset follows (credit cards count booked balances only, negative when owed), plus owned assets and liabilities valued that day as on the Assets page. The Overview shows a Net worth card (in accounts, assets, owed, money at hand and how long it lasts), a Bank data card listing only feeds that are behind (a live feed not synced in two days or with expired access, statements older than a week), and a note when the month has rows still in the Inbox.

   - ~~**Passwords**~~ (done 2026-11-24): `POST /auth/password` changes your own password with the current one and signs out your other sessions. Owners set another member's password with `PUT /households/{id}/members/{userId}/password` (members with a login only), which signs them out everywhere; it's refused (`409 member_in_other_household`) when the member also belongs to a household the owner doesn't own, so one household's owner can't take over a login that opens another. The sidebar's key button and the member's own row change your password; owners get "Set password" on other members' rows.
   - ~~**Income**~~ (done 2026-10-31): dated income lines with a source (payer), account, recipient member (or shared) and notes; negative amounts are clawbacks. The Income page shows the month's total, spending and what was saved, plus a by-source breakdown.
     Not yet: "import typical month", expected-income plan.
     Income categories (done 2026-11-16, V41–V43): what kind of money it was, while the source stays who paid. Category kind `income` beside consumption and investment, and `income.category_id` (earnings only; deductions have none). Expenses, expense lines, split drafts, merchant defaults, split rules and expense rules refuse income categories; income lines and income rules take only income categories; a category in use can't switch to or from income. New households start with Salary, Scholarship, Business, Side work, Family & gifts, Bank bonuses & interest and Other income (V42 and V43 gave existing households the same; a name a spending category already has is skipped, so a household with a "Business" expense category names its own e.g. "Business income"). `GET /income?categoryId=` includes subcategories; the import's income takes `category`/`subcategory`. The Inbox suggests an earning's category from the last row with the same descriptor, else the payer's latest categorised earning (by source, hand-entered ones too), else the interest category for interest. The Categories page lists spending (with investing) and income categories on separate tabs, each adding its own kind, and hues are counted within each; the Income page has a category column and a share bar switching between by category and by source; the Inbox category filter lists income categories after spending ones. Money paid back for shared subscriptions stays out of income, as refunds.
   - ~~**Investments**~~ (done 2026-11-03): market holdings (fund, stock, bond, crypto, other) held by a member or jointly, with dated contributions (negative for withdrawals, optionally from an account) and dated valuations. Each holding shows what went in, what it's worth (latest valuation plus contributions since, at cost), the gain and the gain %. The Overview's Invested is now the month's net contributions; expenses in investment categories still stay out of spending but no longer count as invested, so the same money isn't counted twice.
     Market valuation (2026-11-03): a holding can follow a listed security (search by name, ticker or ISIN) and its contributions record shares; it's then valued daily from closing prices (Yahoo Finance's unofficial keyless API, behind a `MarketData` interface) converted at ČNB fixings, both cached in Postgres and refreshed at most every 6 hours. The Investments page and each holding show worth against money put in over time.
     Fees (2026-11-03): a holding records the fees its provider charged (discounts negative), shown as a running total and in its history. On a holding valued by hand they're informational: the provider already took them out of the value, so they change neither worth nor money put in. On a market-valued holding they're broker commissions paid on top of the shares, so they count as money put in and lower the gain. Each holding breaks them down by year against its average worth (a yearly rate, part years scaled up), and overall against money put in and the gain before fees. Investments show CZK in whole crowns.
     Assets (2026-11-14): investments became assets (tables, API `/assets`, the Assets page). Besides the market kinds (fund, stock, bond, crypto), an asset can be savings, a savings scheme (building savings, pension), money owed to the household, a vehicle, property or other; only market kinds can follow a security, the rest are valued by hand. Past activity entries were renamed with them.
     Liabilities, bank-fed balances, money-weighted return and foreign-currency buys (2026-11-15):
     - Liabilities (`loan`, `card_debt`, `payable`, V27): valuations store what's owed (`>= 0`) and contributions record borrowing (negative) or principal repayments (positive), while `Asset.valueMinor` and `HistoryPoint.valueMinor` report `-owed` so summing every asset gives net worth; `gainMinor` is `0`. `GET /assets/summary` returns Owned / Owed / Net; the Assets page shows Owned / Owed / Net at the top and lists liabilities in their own section. Transfers touching a liability's linked account (`asset_contributions.transfer_id`, V32) automatically create, update and cascade-delete the corresponding repayment or borrowing contribution (read-only in the Assets entry form, with a link back to Transfers; the Inbox and transfer form show "Repays <liability>").
     - Bank-fed balances (V28): `savings`, `scheme`, `other` and liability kinds can link to an account (`assets.account_id`, one asset per account) and read their value and month-end history from its feeds' `bank_balances` converted at ČNB fixings (a liability skips "available" balances, which include an unused credit line), falling back to hand valuations when none exist (`valueSource`: `market` | `bank` | `valuation` | `cost`). Accounts show which asset they feed. Before a feed's first reading, a balance is worked back from it through the feed's bank rows, as far as the day before the feed's import-from day (or first row); the household's `GET /assets/history` carries `accountsMinor` (accounts no holding follows) on each point from the day every account holding something today can be told, and the Assets chart stacks it on worth as a net-worth band (2026-11-21).
     - Money-weighted return (XIRR): `Asset.annualReturn` and `AssetSummary.annualReturn` compute annualised XIRR (Newton–Raphson with bisection fallback on `[-0.99, 10]`; null for liabilities, under 30 days, or when non-convergent), shown as "Yearly return (money-weighted)".
     - Foreign-currency contributions (V29): `asset_contributions` carries `original_amount_minor` and `original_currency`; omitting `amountMinor` on input converts at the date's ČNB fixing, and the entry form defaults to the security's currency with a live converted amount via `/securities/fx`. (Fees in a foreign currency are not yet supported.)
     Review fixes (2026-11-15): a liability reports `repaidMinor` and `borrowedMinor` separately (the Assets page shows Repaid and Borrowed), and its entry form and history speak of what's owed, repayments and borrowing. `gainMinor` is null when nothing was recorded going in (a savings account read from the bank, a car valued by hand), and the summary's gain counts only assets money was put into. A liability ignores "available" bank balances, which include an unused credit line, and falls back to hand valuations with a note (`bankAvailableOnly`). `Market.refreshFx` fetches a date's ČNB year and, when that year has no fixing on or before the date (January 1), the year before; contributions, `/securities/fx`, the Assets page, the inbox, rules, transfers and the bank sync all use it.

     - Members without a login: owners add them by name, and they can't sign in. An invite can name one to claim, and whoever accepts takes their place, with everything that was theirs moving across through cascading references.
     - Accounts have a kind (bank, credit card, cash, other) and an optional IBAN, checked and unique per household.
     - Trips have optional dates and a Trips page with what each cost. An expense can belong to a trip.
     - An expense can record what it cost in another currency.
     - Income carries the month it was earned, which the Income page and Overview count it in, as well as the date it arrived.
